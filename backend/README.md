# Forge Backend

FastAPI + SQLAlchemy + Alembic backend for Forge, backed by a self-hosted Postgres database. Replaces the app's previous Supabase-based backend (Auth, Postgres, Storage, Edge Functions) entirely — no Supabase dependency remains.

## Stack

- **API**: FastAPI
- **DB**: SQLAlchemy 2.0 (ORM) against Postgres, via `psycopg` 3
- **Migrations**: Alembic, autogenerated from the SQLAlchemy models in `app/models/`
- **Auth**: self-rolled JWT (access + refresh tokens), passwords hashed with `bcrypt` directly
- **File storage**: local disk (`storage/`), served back through an authenticated endpoint — swappable for S3-compatible storage later without changing the API contract
- **AI**: the user's choice of Anthropic (Claude) or Google Gemini (`user_profiles.ai_provider`), called only from `POST /plans/generate` via `app/services/ai_providers.py`. Prefers the user's own key for that provider (`PUT /ai-keys/{provider}`) over the server's shared fallback key (`ANTHROPIC_API_KEY` / `GEMINI_API_KEY`; if only the other provider has a shared key, that one is used). Shared-key generations are limited per user per local day (`SHARED_KEY_DAILY_PLAN_LIMIT`, default 5; `GET /plans/usage`); users with their own key are unlimited.

## Setup

1. **Postgres**: point `DATABASE_URL` at your own Postgres instance. For local dev, a `forge` role + database were created on a local Postgres 18 server:
   ```sql
   CREATE ROLE forge WITH LOGIN PASSWORD 'forge';
   CREATE DATABASE forge OWNER forge;
   ```
2. **Python env**:
   ```bash
   python -m venv .venv
   source .venv/Scripts/activate   # or .venv/bin/activate on macOS/Linux
   pip install -r requirements.txt
   ```
3. **Environment**:
   ```bash
   cp .env.example .env
   ```
   Fill in `DATABASE_URL`, a random `JWT_SECRET` (generate with `python -c "import secrets; print(secrets.token_urlsafe(48))"`), a `DATA_ENCRYPTION_KEY` (generate with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` — **back it up**, see Design notes), and optionally `GEMINI_API_KEY` and/or `ANTHROPIC_API_KEY` as the shared key every user gets (subject to the daily limit).

   **Email (verification + password reset codes):** set the `SMTP_*` values to send real email (for Gmail: `smtp.gmail.com`, port 587, an App Password). Leave `SMTP_HOST` empty in local dev and codes are printed to the backend's console instead — look for `[email:dev-fallback]` in the uvicorn output.
4. **Run migrations**:
   ```bash
   alembic upgrade head
   ```
5. **Seed the exercise glossary** (one-time, ~876 exercises from [free-exercise-db](https://github.com/yuhonas/free-exercise-db)):
   ```bash
   python -m scripts.seed_exercises
   ```
6. **Run the server**:
   ```bash
   uvicorn app.main:app --reload --port 8000
   ```
   Interactive API docs: `http://localhost:8000/docs`.

## Project structure

```
app/
  main.py           # FastAPI app, router registration, CORS
  core/
    config.py         # pydantic-settings, reads .env
    database.py        # SQLAlchemy engine/session/Base
    security.py         # password hashing, JWT create/decode
    deps.py               # get_current_user dependency
  models/            # SQLAlchemy ORM models (one file per domain area)
  schemas/            # Pydantic request/response models
  api/               # FastAPI routers (one per resource)
  services/           # Business logic: personal records, plan generation/prompt/summary, Anthropic client
alembic/
  versions/           # migration files
scripts/
  seed_exercises.py    # one-time exercise glossary seed
storage/              # uploaded files (progress photos), gitignored
```

## API overview

| Area | Routes |
|---|---|
| Auth | `POST /auth/sign-up`, `POST /auth/verify-email`, `POST /auth/resend-verification`, `POST /auth/sign-in`, `POST /auth/refresh`, `POST /auth/forgot-password`, `POST /auth/reset-password`, `PATCH /auth/username` |
| Profile | `GET/PATCH /profile`, `POST /profile/complete-onboarding` |
| Exercises | `GET /exercises`, `GET /exercises/{id}`, `GET /exercises/muscle-groups`, `GET /exercises/equipment-options`, `GET /exercises/feedback/all`, `PUT /exercises/{id}/feedback` |
| Workouts | `GET /workouts`, `POST /workouts` (manual log), `GET /workouts/{id}/sets`, `PATCH /workouts/{id}` (rate) |
| Measurements | `GET/POST /measurements`, `DELETE /measurements/{id}`, `GET /measurements/types`, `GET/POST /measurements/photos`, `GET /measurements/photos/{id}/file`, `DELETE /measurements/photos/{id}` |
| Personal records | `GET /personal-records` |
| Stats | `GET /stats/overview?tz=<IANA zone>` — this vs last month, milestones, strength gains, lifetime totals |
| AI keys | `PUT /ai-keys/{anthropic|gemini}`, `DELETE /ai-keys/{anthropic|gemini}` |
| Plans | `POST /plans/generate?tz=` (202, runs in the background; 429 past the daily shared-key limit), `GET /plans/generation` (progress), `GET /plans/usage?tz=` (today's shared-key generations), (optional body `{preferences: {training_days, day_focus: {day: [muscles]}, include_warmup, session_minutes, notes}}`), `GET /plans`, `GET /plans/latest`, `PATCH /plans/{id}` |

Every route except auth and `GET /exercises*` requires `Authorization: Bearer <access_token>` (`PATCH /auth/username` needs it too).

### Auth flow

1. `sign-up` (email + username + password) creates an unverified account and emails a 6-digit code. No tokens yet.
2. `verify-email` exchanges that code for tokens. `sign-in` returns 403 until the email is verified. `resend-verification` issues a fresh code.
3. `sign-in` takes an `identifier` that can be either the email or the username.
4. `forgot-password` emails a reset code; `reset-password` (code + new password) sets the password and returns tokens.

`resend-verification` and `forgot-password` always answer 204 so they can't be used to check which emails have accounts. Codes are single-use, expire after `EMAIL_CODE_EXPIRE_MINUTES`, and only the newest code for a purpose is valid.

## Design notes

- **Sensitive data is encrypted at rest** (`app/core/crypto.py`, `app/core/encrypted_types.py`), keyed by `DATA_ENCRYPTION_KEY` from `.env` — never stored in the database, so a database dump or backup on its own reveals none of it:
  - *Encrypted* (Fernet — AES-128 + HMAC, random IV; the app decrypts on read): `users.email`, `integration_tokens.access_token` (users' AI keys), `user_profiles.gender` / `birth_year` / `height_cm` / `plan_preferences`, `measurements.value`, `progress_photos.notes` and the photo files on disk, `workouts.notes`, `generated_plans.source_summary`. These columns can't be filtered or aggregated in SQL; the model column types handle it transparently.
  - *Hashed* (never readable, only compared): passwords (bcrypt), email codes (`email_codes.code_hash`, HMAC-SHA256 keyed by the same secret so a leaked table can't be brute-forced). Emails are looked up through `users.email_hash`, a keyed hash of the lower-cased address.
  - *Not encrypted*, because the app queries or aggregates them: usernames (public handle, used to sign in), workout dates/titles and set weights/reps (stats, personal records), exercise feedback, measurement type/date, plan contents. Put Postgres and `STORAGE_DIR` on encrypted disks (any managed Postgres does this by default) to cover these too.
  - **Losing `DATA_ENCRYPTION_KEY` makes the encrypted data unrecoverable** — including every user's email, so nobody could sign in by email. Keep it in a secrets manager / password manager, separate from database backups. There is no key rotation yet.
- **RLS is gone; authorization is enforced in Python.** Every query that touches user-owned data filters by `current_user.id` explicitly in the route/service code (see any `filter(Model.user_id == current_user.id)` call) — there's no database-level row security layer doing this automatically anymore, so a new endpoint that forgets this filter is a real bug class to watch for in review.
- **Plan generation runs in the background.** `POST /plans/generate` stores a `generated_plans` row with `status='generating'`, returns 202 at once, and a FastAPI background task makes the AI call and flips the row to `ready` or `failed` (with a user-facing `error`). One job per user at a time (409 otherwise); jobs lost mid-flight (server restart) are marked failed after 6 minutes. `GET /plans`, `/plans/latest` only return `ready` plans.
- **Gemini falls back across models.** On 429/5xx/timeouts/404 the Gemini client tries the next model in `GEMINI_MODEL` + `GEMINI_FALLBACK_MODELS` (default `gemini-3.8-flash` → `gemini-3.7-flash` → `gemini-3.5-flash-lite`); key errors fail immediately. The model actually used is saved in the plan's `source_summary.model`.
- **Plan preferences shape the prompt.** Training days, the muscles for each day (individual muscles only, any number per day, never pre-grouped), warm-up on/off, session length and a free-text note (all optional) go into a dedicated prompt section; they're saved to `user_profiles.plan_preferences` as the very first step of `POST /plans/generate` (so they survive a rejected or failed generation) and pre-fill the form next time; each plan also keeps its own copy in `source_summary.preferences`.
- **AI keys (Anthropic and Gemini) and any future third-party secrets live in `integration_tokens`**, which has no route exposing `access_token` in a response — only internal services read it.
- **`POST /plans/generate` is the only endpoint with a real per-call cost** — it's never called automatically; the frontend only calls it from an explicit user action.
- **Brute-force protection on auth.** Each emailed code allows 5 wrong guesses before it's burned, and a user can be issued at most 5 codes of each kind per hour — so a 6-digit code can't be guessed within its expiry window. On top of that, `app/core/rate_limit.py` rate-limits the unauthenticated auth routes per client IP (sign-in 10/min, code checks 10/min, sign-up and code sends 5 per 10 min), returning 429.
- **Plan exercises are linked to the glossary server-side.** The prompt only lists exercise *names* (filtered to the athlete's equipment, training categories, and — for beginners — non-advanced movements, capped at 250). After Claude answers, `_attach_exercise_ids` fills each plan exercise's `exercise_id` by exact name match; anything Claude invented outside the glossary keeps `exercise_id: null`.
- **Personal records are recomputed synchronously** inside `POST /workouts`, not via a DB trigger, mirroring the previous client-side logic — kept in `app/services/personal_records.py` so the "new PR" moment stays easy to detect from the same request that created it.

## Known follow-ups

- No automated tests yet.
- Auth rate limiting is in-process memory: it resets on restart and isn't shared between multiple workers/instances. Move it to Redis or the reverse proxy if you scale out, and run uvicorn with `--proxy-headers` behind a proxy so limits apply to the real client IP.
- Refresh tokens aren't tracked/revocable server-side (no refresh-token table) — a stolen refresh token stays valid until it expires. Add a revocation list or rotate-and-store pattern if that matters for your deployment.
- Local-disk file storage doesn't survive a redeploy on most PaaS platforms (ephemeral filesystems) — move to S3-compatible storage before deploying anywhere other than a persistent VM/server you control.
